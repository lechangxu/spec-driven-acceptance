# spec-driven-acceptance（中文镜像）

**先写规格，再让机器判定活干完没有。**（[English](README.md)）

把任务交给 AI 编码代理时，失败几乎都发生在同一处：没人事先约定「完成」长什么样， 于是代理宣布完成，人再读 diff，指望看得出问题。这个仓库把那层判定写下来。

## 问题

- 「做完了」是想要收工的人自己作出的声明。
- 评审注意力稀缺且分布不均，一天里的第十个 diff 往往只被扫一眼。
- 评审质量不可见：没人记录它放过了多少缺陷。

## 方法

六层，从便宜到贵。每层都要写明：它保证什么、抓不到什么、失败该退回哪一层。

1. **规格**——把需求写成行为，而不是意图。
2. **任务卡**——把规格冻结成文档，同时携带决策、风险点、验收与边界。
3. **机器判据**——每条验收写成命令加期望结果，「完成」是退出码，不是一句话。
4. **确定性扫描**——只扫新增行，抓那些机械可辨的坏形状。
5. **独立评审**——评审者没写过这段代码，也没被要求友善。
6. **反馈度量**——两类错误都要计数，管线本身才可调。

完整走查（含数据流图）见 [docs/acceptance-pipeline.md](docs/acceptance-pipeline.md)； 失效面另见 [评审独立性](docs/judge-
independence.md) 与 [误判率监控](docs/misjudgment-monitoring.md)。

## 快速开始

任务卡是产物本身。拿示例卡跑校验器：

```bash
python3 card_lint.py examples/task-card.example.md
```

可机械验收时打印 `OK` 并 exit 0；删一节或让某条判据丢掉命令就 exit 1 并点名； 文件读不到或参数不对则 exit 2——「没法检查」≠「检查过且没问题」。

它强制的形状：六节 `Goal` / `Decisions` / `Spec` / `Risks` / `Acceptance` / `Boundaries`； 验收判据 ≥2
条；每条判据同时含反引号命令与 `Expected`；`Risks` ≥1 条。

它故意**不**判断这条命令是否真能证明那个主张——那是写卡时人做一次的决定。

跑测试：

```bash
python3 -m unittest discover -s tests -v
```

除标准库外无依赖，Python 3.9+。

## 这不是什么

不是框架、不是服务、也不是模型的封装。它就是一套文档范式加九十行 Python， 用来强制那个形状。有意思的是论证，不是代码。

## 局限

- 全绿只证明判据被满足，判据本身可能很弱。
- 校验器只查形式；卡可以形状完美却描述错了东西。
- 为小而可审的 diff 调校；巨大改动先换拆法。
